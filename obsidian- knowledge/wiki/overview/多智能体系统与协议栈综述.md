# 多智能体系统与协议栈综述

> 2026 年，多智能体系统已收敛于编排器+子智能体模式，协议栈（A2A/MCP/REST）已形成三层互补架构。本综述整合两个知识域，呈现本项目知识图谱中的智能体系统全景。

## 设计背景

随着 AI 智能体从单一模型走向多智能体协作，两个核心架构问题随之浮现：

1. **如何组织智能体**？——单一智能体 vs 多智能体，编排方式如何选型
2. **如何让智能体通信**？——A2A、MCP、REST 各自解决什么，如何协同

这两个问题相互交织——通信协议的选择直接影响多智能体系统的架构设计，反之亦然。

### 协议栈的三层角色

```
         ┌─────────────┐
         │   A2A       │ ← 智能体间通信（水平）
         │  (协作层)    │   解决 "谁来做"
         ├─────────────┤
         │   MCP       │ ← 智能体-工具集成（垂直）
         │  (工具层)    │   解决 "用什么做"
         ├─────────────┤
         │ REST/HTTP   │ ← 基础设施传输
         │  (传输层)    │   解决 "怎么传"
         └─────────────┘
```

三层互补而非替代。成熟的多智能体系统三层都需要。

## 协议栈深度对比

| 维度 | A2A 协议 | MCP 协议 | 传统 REST API | 三者协同 |
|------|---------|---------|--------------|---------|
| **通信方向** | 智能体↔智能体（水平） | 智能体→工具（垂直） | 客户端↔服务器（请求-响应） | 三层并行，覆盖全链路 |
| **标准化层级** | 智能体协作语义 | 工具调用语义 | HTTP 传输层 | 语义解耦，可独立演进 |
| **核心问题** | "我有一个智能体，其他智能体来找我协作" | "我有一个工具，智能体来用" | "我有一个接口，你来调用" | 覆盖 AI 系统全通信场景 |
| **发现机制** | Agent Card（`/.well-known/agent-card.json`） | `list_tools` 原语 | 文档手动对接 | 自动+手动，分层发现 |
| **对话/任务管理** | Task 生命周期跟踪 | 有状态 Session | 无状态（每次独立） | 不同粒度的状态管理 |
| **流式支持** | JSON-RPC + SSE/gRPC | 原生 SSE 流 | SSE/WebSocket 自建 | 统一流式架构 |
| **企业就绪** | 签名 Agent Card + 多租户 | OAuth 2.1 内置 | 认证需自建 | 渐进式企业化 |
| **治理成熟度** | 增长中（v1.0，150+ 组织） | 高（AAIF，9700 万+ SDK 月下载） | 成熟（几十年） | 互补成熟度 |
| **本项目状态** | ⏳ 待集成 | ✅ 已用（3003/3004） | ✅ 已用（Ollama API） | 渐进式演进 |

## 多智能体系统设计模式

| 模式 | 描述 | 适用场景 | 失败率 | Token 开销 | 协议需求 |
|------|------|---------|--------|-----------|---------|
| **单一智能体** | 一个 Agent 做所有事 | ≤5 步，工具 <5，单域 | 约 20% | 基准 | 仅 MCP + REST |
| **编排器+子智能体** ⭐ | 编排器分解→执行→聚合 | 多域、可并行、大量只读 | 41-87%（79% 因协调失败） | +58%~285% | MCP + A2A |
| **GroupChat** ❌ | 点对点自由协作 | 已被证明低效，已淘汰 | 高 | 高 | 仅 A2A |

### 选型决策树

```
任务复杂度高？
├─ 否 → 单一智能体（默认选择，~80% 场景）
└─ 是 → 可拆分为独立子任务？
        ├─ 否 → 单一智能体
        └─ 是 → 子任务需要不同专长？
                ├─ 否 → 单一智能体（并行批处理即可）
                └─ 是 → 多智能体系统（编排器+子智能体）
```

### 智能体通信流程

```
人类提问
  ↓
build Agent（主导 Agent）
  │
  ├─ MCP ──→ Graph RAG MCP ──→ query_route/vector_search（知识检索）
  ├─ MCP ──→ Obsidian MCP ──→ read_file（读取页面）
  │
  ├─ (未来) A2A ──→ query-agent ──→ 并行深度查询
  ├─ (未来) A2A ──→ lint-agent ──→ 并行健康检查
  └─ (未来) A2A ──→ ingest-agent ──→ 异步知识摄入
  ↓
build Agent 综合结果 → 回答
```

### 设计原则

| 原则 | 实现 | 理由 |
|------|------|------|
| **单一主导 Agent** | build 独自与用户交互 | 保证对话上下文连贯性 |
| **后台并行处理** | lint/ingest 由子 Agent 异步处理 | 不打断主对话 |
| **统一模型** | 全部使用 deepseek-v4-flash-free | 云端统一推理，消除本地模型切换与常驻开销 |
| **MCP 优先** | 先满足工具调用需求 | 当前工具集成 > 智能体协作 |
| **A2A 待集成** | 等待生态成熟 | 避免过早绑定未稳定协议 |

## 知识图谱关系总结

### 核心关系流

```
多智能体系统
  ├── 使用 ──→ A2A 协议    （智能体间水平通信）
  ├── 使用 ──→ MCP Server  （智能体→工具垂直集成）
  ├── 使用 ──→ REST API    （基础设施传输层）
  ├── 包含 ──→ 编排器 Agent（build）
  ├── 包含 ──→ 子智能体    （query/lint/ingest）
  └── 基于 ──→ 大语言模型  （推理核心）
```

### 协议间关系

```
A2A 协议 ←──互补──→ MCP Server
    │                    │
    ├── 使用 SSE 传输    ├── 使用 SSE 传输
    ├── 基于 Agent Card  ├── 基于 list_tools
    └── AAIF 管理        └── AAIF 管理

传统 REST API ──传输基础──→ 两者之上
```
