# MCP vs A2A vs 传统API

> 2026 年 AI 集成的三种协议栈：MCP 连接工具，A2A 连接智能体，传统 REST API 仍是基础设施。

## 对比维度

| 维度 | 传统 REST API | MCP（Model Context Protocol） | A2A（Agent-to-Agent） |
|------|-------------|------------------------------|----------------------|
| **标准化层级** | HTTP 传输 | 工具调用语义 | 智能体协作语义 |
| **方向** | 客户端 → 服务器 | 智能体 → 工具 | 智能体 ↔ 智能体 |
| **类比** | 打电话问信息 | 插 USB 设备 | 两台电脑联网 |
| **发现机制** | 文档手动对接 | 工具列表（`list_tools`） | Agent Card（`/.well-known/agent-card.json`） |
| **对话管理** | 无状态，每次独立 | 有状态 Session | Task 生命周期跟踪 |
| **流式支持** | SSE/WebSocket 自建 | 原生 SSE 流 | JSON-RPC + SSE/gRPC |
| **企业就绪** | 认证需自建 | OAuth 2.1 内置 | 签名 Agent Card + 多租户 |
| **治理成熟度** | 成熟（几十年） | 高（97M+ SDK 月下载量，AAIF 管理） | 增长中（v1.0，150+ 组织） |

## 谁解决什么问题

```
传统 REST API ── "我有一个接口，你来调用"
    ↓ 标准化调用协议
MCP ─────────── "我有一个工具，智能体来用"
    ↓ 标准化智能体协作  
A2A ─────────── "我有一个智能体，其他智能体来找我协作"
```

### 传统 REST API
- **核心价值**：成熟、稳定、任意语言可用
- **短板**：每次对接需要读文档、写适配代码
- **适合**：基础设施层、对外公开的服务

### MCP
- **核心价值**：智能体无需预先知晓工具的接口细节，运行时发现
- **短板**：只解决智能体-工具，不解决智能体-智能体
- **适合**：让 LLM 操作文件系统、数据库、浏览器、API

### A2A
- **核心价值**：跨框架、跨供应商的智能体互操作
- **短板**：新协议，生态仍在扩展中
- **适合**：多智能体系统间的任务委派和结果交换

## 本项目的集成现状

| 协议 | 状态 | 用途 |
|------|------|------|
| **REST API** | ✅ 已用（Ollama API） | 本地模型推理调用 |
| **MCP** | ✅ 已用（Obsidian MCP + Graph RAG MCP） | 知识库操作、图谱检索 |
| **A2A** | ⏳ 待集成 | 跨工具智能体协作（未来） |

## 三层协议栈的未来

```
         ┌─────────────┐
         │   A2A       │ ← 智能体间通信
         │  (水平)      │
         ├─────────────┤
         │   MCP       │ ← 智能体-工具集成
         │  (垂直)      │
         ├─────────────┤
         │ REST/HTTP   │ ← 基础设施
         │  (传输)      │
         └─────────────┘
```

三层互补而非替代。**成熟的多智能体系统三層都需要**。
