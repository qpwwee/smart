# 多智能体 vs 单一智能体 适用场景对比

> 2026 年多智能体系统已收敛于编排器+子智能体模式。核心问题不是"哪个更好"，而是"你的任务需要多少智能体"。

## 对比维度

| 维度 | 单一智能体 | 多智能体系统 |
|------|-----------|-------------|
| **架构复杂度** | 低，一个智能体做所有事 | 高，需要编排+通信+协调 |
| **任务并行能力** | 串行处理 | 可并行（+16% 吞吐提升） |
| **失败率** | 低（~20%） | 高（41-87%，79% 源于协调失败） |
| **额外 Token 开销** | 无 | 集中式 ~285%，独立式 ~58% |
| **调试难度** | 低，端到端追踪 | 高，需要追踪跨智能体通信 |
| **专业分工** | 一个模型胜任所有子任务 | 各智能体可专精不同领域 |
| **可扩展性** | 受限于模型上下文窗口 | 可通过增加智能体扩展 |
| **适用场景** | 大多数单域任务 | 可并行、大量读取、多专家领域 |

## 选择标准

### 选单一智能体（默认选择）
- 任务步骤不超过 5 步
- 所需工具少于 5 个
- 无需长时间并行工作
- 失败成本高（如生产环境写操作）
- 你的场景 80% 属于此类

### 选多智能体系统
- 任务可以明确拆分为多个独立子任务
- 子任务可并行执行
- 不同子任务需要不同专业知识/模型
- 容错：某个智能体失败不影响整体
- 需要大量只读操作（代码审查、文档分析）

## 2026 年行业共识

业界已收敛到**编排器 + 子智能体**模式：
- **编排器**：拥有完整对话上下文，负责分解任务、分配子任务
- **子智能体**：短暂存在，完成特定子任务后返回压缩摘要
- GroupChat（点对点协作）已被证明 [[A2A 协议]]效率低下，逐渐淘汰

**主流实现**：
- Anthropic Claude Code — Agent 团队模式
- OpenAI Agents SDK — 层级式编排
- [[OpenCode]] Agent Teams — 扁平团队架构（1 主导 + N 队友） 基于-关系（多智能体 vs 单一智能体 适用场景对比**基于**OpenCode）

## 本项目的配置

| 智能体 | 类型 | 职责 | 模型 |
|--------|------|------|------|
| build (默认) | 主导 | 综合查询 + Wiki 维护 | deepseek-v4-flash-free（云端） |
| query-agent | 子智能体 | 知识查询专家 | deepseek-v4-flash-free（云端） |
| lint-agent | 子智能体 | 健康检查专家 | deepseek-v4-flash-free（云端） |
| ingest-agent | 子智能体 | 知识摄入专家 | deepseek-v4-flash-free（云端） |

> 📝 **历史模型**：此前使用 `gemma4:e4b`（build）和 `gemma4-cn`（子智能体），本地推理模型已全部卸载，当前统一使用云端 `deepseek-v4-flash-free`。

**为什么这样设计？**
- 用户交互由单一 build 主导，保证上下文连贯性
- 后台任务（lint/ingest）由子智能体并行处理，不打断主对话
- 所有子智能体返回压缩摘要，避免编排器上下文膨胀
- 统一云端模型，消除本地模型加载和常驻开销
